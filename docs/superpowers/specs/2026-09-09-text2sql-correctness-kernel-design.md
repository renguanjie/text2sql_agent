# Text2SQL 正确性内核设计规格

## 1. 背景与定位

项目将聚焦为“中文、本地模型友好、具有语义治理和安全执行能力的 Text2SQL 服务”。当前代码已经具备 Schema 抽取、Neo4j 知识检索、SQL 生成、AST 安全校验、查询范围限制、执行超时与行数限制，但仍缺少三个闭环：

1. 可由 Git 审查和回滚的业务语义真相源；
2. 从生成结果到数据库预检的确定性正确性校验；
3. 可量化回归的中文问题评测集。

本规格只覆盖第一阶段“正确性内核”。它在现有 `SQLGenerator` 链路中渐进集成，不新建独立服务，不扩展新的数据库类型，也不实现用户鉴权和管理后台。

## 2. 目标与成功标准

### 2.1 目标

- 使用 Git 管理的 YAML 作为唯一人工语义真相源。
- 将 YAML 编译为排序稳定、可校验、可追踪版本的规范化 JSON 快照。
- 让本地小模型只接收与当前问题相关的紧凑中文语义上下文。
- 在执行前确定性验证表、字段、关联、指标、时间维度和安全范围。
- 对失败 SQL 只允许一次基于结构化错误的模型纠错，二次失败时关闭执行。
- 通过中文 Golden Set 对不同模型和语义版本进行可重复评测。

### 2.2 成功标准

- 非法语义模型不能成为激活版本，旧的有效快照继续可用。
- SQL 引用未知表、未知字段、未治理关联或错误指标表达式时不能进入执行阶段。
- 开启预检后，MySQL `EXPLAIN` 失败、超时或返回不可接受结果时不能执行查询。
- 单次请求的模型纠错次数恒定不超过 1。
- 同步与异步生成入口执行相同的验证状态机并返回相同结构。
- Golden Set 能输出用例级结果及按模型、语义版本汇总的通过率。
- 未启用新能力时，现有调用方和默认行为保持兼容。

## 3. 非目标

- 本阶段不实现 FastAPI、鉴权、RBAC、租户隔离或管理界面。
- 本阶段不新增 PostgreSQL、SQLite、DuckDB 等连接器。
- 本阶段不允许 Neo4j 或运行时 UI 修改 Git 语义定义。
- 本阶段不让模型自行发布语义模型或自动接受推断出的指标定义。
- 本阶段不以 SQL 字符串完全相等作为正确性标准。

## 4. 总体架构

采用“渐进式正确性内核”，保留现有 Streamlit、MySQL、Neo4j、检索器和 `SQLGenerator` 公共入口。

新增四个边界清晰的组件：

1. **Semantic Compiler**：读取 YAML、执行结构和跨引用校验、生成规范化 JSON 与版本清单。
2. **Semantic Registry**：以只读方式加载已编译快照，按数据源提供不可变的激活版本。
3. **Correctness Pipeline**：统一同步和异步路径的语法、安全、语义、预检与一次纠错状态机。
4. **Golden Evaluator**：执行结构断言和可选结果断言，生成机器可读评测报告。

Neo4j 是已发布语义的检索索引，不是事实来源。SQL 校验必须使用 Semantic Registry 中的激活快照；Neo4j 不可用时可以降低召回质量，但不能绕过语义校验。

## 5. 语义模型

### 5.1 源文件约定

人工源文件位于 `semantic_models/<datasource>.yaml`。每个文件必须包含：

- `schema_version`：文件格式版本，第一版固定为 `1`；
- `model_version`：遵循 SemVer 的业务语义版本；
- `datasource`：稳定数据源标识；
- `dialect`：第一阶段只允许 `mysql`；
- `entities`：表及其中文业务语义；
- `relationships`：允许使用的表关联；
- `metrics`：受治理的指标公式；
- `terms`：中文术语、别名和歧义消解规则；
- `policies`：允许、禁止或敏感的对象声明。

实体字段支持物理列名、中文名、同义词、数据类型、角色、值域和敏感级别。字段角色只允许 `identifier`、`dimension`、`measure`、`time`。指标必须声明聚合表达式、允许维度、必需过滤条件和默认时间字段。关系必须声明两端实体与字段、连接类型及可选附加条件。

首版不在 YAML 中存放数据库凭据、真实业务数据或提示词模板。

### 5.2 编译产物

编译产物位于 `semantic_models/.compiled/<datasource>/<model_version>.json`，清单位于 `semantic_models/.compiled/manifest.json`。产物必须：

- 使用确定性键顺序和 UTF-8 编码；
- 包含 `source_sha256`、`compiled_at`、编译器版本和模型版本；
- 通过随代码发布的 JSON Schema 校验；
- 在相同源文件和编译器版本下生成相同的语义内容摘要。

`compiled_at` 不参与内容摘要。激活版本由清单明确指定，不依据文件修改时间推断。

### 5.3 编译校验

编译器必须拒绝以下情况：

- 重复实体、字段、指标或术语；
- 关系、指标或策略引用不存在的对象；
- 指标使用未声明字段或未允许聚合；
- 同一中文别名无消歧条件地指向多个对象；
- 模型版本非法、数据源不一致或方言不受支持；
- 敏感字段被同时声明为可直接查询字段。

加载新快照采用“先完整校验、再原子替换”。校验失败时保留当前有效快照，并返回明确错误，不静默加载部分内容。

## 6. 生成与验证数据流

每次请求固定经过以下阶段：

1. 规范化中文问题，但保留原始文本用于审计指纹。
2. 根据术语、实体、指标和关系检索最小语义切片。
3. 将紧凑的中文语义切片、Schema 和合格 Few-Shot 注入模型。
4. 提取单条 SQL，并执行现有 AST 语法及只读安全校验。
5. 使用激活语义快照校验表、字段、关系、指标、时间维度和治理策略。
6. 对通过确定性校验的 MySQL SQL 执行带超时的 `EXPLAIN`。
7. 若第 4、5 或 6 阶段失败，生成结构化错误并允许模型纠错一次。
8. 对修复后的 SQL 从第 4 阶段重新执行全部校验；任何失败均终止。
9. 使用现有行数和超时约束重写查询，再交给执行器。
10. 只有真实执行成功的记录才能进入 Few-Shot 索引。

语义切片需设置字符和条目上限。优先级依次为命中的指标、实体、字段、关系、术语和策略；达到上限后不追加低优先级内容。不得因为上下文截断而删除与命中指标相关的必需关系或策略。

## 7. 语义校验规则

首版实现以下确定性规则：

- `UNKNOWN_TABLE`：引用的物理表不属于激活模型。
- `UNKNOWN_COLUMN`：字段不存在或无法在别名作用域中解析。
- `AMBIGUOUS_COLUMN`：无表前缀字段能匹配多个输入表。
- `INVALID_JOIN`：表之间没有已治理关系，或 `ON` 字段与关系定义不匹配。
- `METRIC_MISMATCH`：问题命中受治理指标，但 SQL 聚合表达式不等价。
- `DIMENSION_NOT_ALLOWED`：指标按未允许维度聚合。
- `TIME_DIMENSION_REQUIRED`：问题包含时间范围或粒度，但 SQL 未使用受治理时间字段。
- `POLICY_DENIED`：引用禁用表、字段或不允许直接查询的敏感字段。
- `EXPLAIN_FAILED`：数据库拒绝预检、预检超时或预检结果不可接受。
- `SEMANTIC_VERSION_MISMATCH`：生成上下文和校验阶段使用的快照版本不同。

AST 等价判断优先于字符串比较。首版只支持可确定解析的常见聚合、过滤和连接表达式；无法证明正确时按失败处理，不让模型猜测后直接执行。

## 8. 有限纠错协议

纠错输入只包含：原始问题、失败 SQL、语义版本、错误码列表、脱敏错误说明，以及与错误对象相关的最小语义切片。

纠错输入不包含数据库原始异常、连接信息、样例真实值、完整日志或无关 Schema。模型必须返回单条 SQL，不返回解释文本。状态机维护 `repair_attempts`，初始为 `0`，调用纠错前原子增加为 `1`；当其为 `1` 时任何失败直接返回，不得再次调用模型。

输出结果统一包含：

- `status`：`success`、`rejected` 或 `error`；
- `sql`：最后一次候选 SQL；
- `semantic_version`：实际校验版本；
- `validation`：各阶段结果和结构化错误；
- `repair_attempts`：`0` 或 `1`；
- `executable`：只有全部检查通过时为 `true`。

内部异常使用随机错误编号记录；对外只返回稳定错误码和脱敏描述。

## 9. MySQL 预检

第一阶段仅实现 MySQL `EXPLAIN`。预检与正式查询使用相同的只读连接和超时上限，但不读取业务结果集。预检前仍须完成 AST、安全范围和语义校验。

以下情况关闭执行：

- `EXPLAIN` 返回数据库错误；
- 达到预检超时；
- 查询计划为空；
- 配置了扫描行数阈值且估算扫描行数超过阈值。

数据库原始错误只进入受控日志，并经过现有脱敏工具处理。对外纠错信息使用归一化错误类别，不泄露 SQL 字面量或数据库拓扑。

## 10. 中文 Golden Set

评测用例位于 `eval/golden/*.yaml`。每个用例包含：

- 稳定用例 ID、中文问题、数据源和方言；
- 期望及禁止出现的表、字段和指标；
- 期望关系、过滤条件和时间粒度；
- 是否应允许执行；
- 可选的结果列、行数范围或稳定数据集结果摘要。

评测器使用 sqlglot AST 和语义校验结果进行结构比较，不要求 SQL 文本完全一致。默认离线模式不执行数据库查询；显式开启集成模式且提供隔离测试库时才比较结果摘要。

报告写为 JSON，包含模型标识、模型参数摘要、语义版本、代码提交、总通过率、各规则通过率、失败错误码和耗时。问题文本和 SQL 只记录摘要指纹；只有显式调试开关允许在本地报告中保留全文。

## 11. 配置与兼容性

新增配置采用显式开关：

- `SEMANTIC_GOVERNANCE_ENABLED=false`
- `SEMANTIC_MODEL_DIR=semantic_models`
- `SEMANTIC_DATASOURCE=default`
- `SQL_REPAIR_MAX_ATTEMPTS=1`
- `SQL_EXPLAIN_ENABLED=false`
- `SQL_EXPLAIN_TIMEOUT_MS=3000`
- `SQL_EXPLAIN_MAX_ESTIMATED_ROWS=0`，其中 `0` 表示不按估算行数拒绝。

启用语义治理时，`SQL_REPAIR_MAX_ATTEMPTS` 只允许 `0` 或 `1`。配置错误必须在组件初始化阶段失败，不在请求中途降级。旧功能在两个主开关均为 `false` 时保持现有行为。

## 12. 安全、日志与可观测性

- 语义源文件和编译产物不得包含凭据或真实业务值。
- 所有 SQL、问题和数据库错误沿用脱敏与指纹化日志策略。
- 每次请求记录语义版本、阶段耗时、错误码、是否纠错和是否可执行，不记录完整敏感内容。
- 评测报告和运行日志不得成为 Few-Shot 数据源。
- 只有通过全量校验并真实执行成功的历史记录可以晋升为 Few-Shot。

## 13. 实现边界

计划新增 `core/semantic/`、`semantic_models/`、`eval/` 及对应测试；修改 `core/sql/generator.py`、`core/chain/sql_chain.py`、`core/history/mysql_client.py`、`core/app_context.py`、`config.py` 和 `env.example`。现有 `core/sql/validator.py` 保留安全校验职责，已有 `core/sql/field_validator.py` 的 AST 解析能力迁移或复用到新的语义校验器，避免维护两套字段解析规则。

不进行与正确性内核无关的 UI 重写、数据库抽象或目录大迁移。

## 14. 测试与验收

测试分为四层：

1. 编译器单元测试：合法模型、重复项、断链引用、歧义别名、确定性摘要和原子激活。
2. 语义校验器单元测试：别名作用域、CTE、连接、指标、时间维度和策略规则。
3. 管线测试：同步/异步一致性、一次纠错上限、版本钉住、EXPLAIN 失败关闭执行、Few-Shot 晋升条件。
4. Golden Set 测试：离线结构评分、报告格式、敏感内容默认不落盘。

验收时运行全部现有测试、新增单元测试、Ruff 和 Python 编译检查。数据库相关测试默认标记为集成测试，在配置隔离测试库后单独执行。

## 15. 交付顺序

1. 语义模型类型、JSON Schema、编译器和注册表；
2. AST 语义校验器及结构化错误；
3. MySQL EXPLAIN 预检器；
4. 同步/异步统一正确性管线和一次纠错；
5. 中文 Golden Set、评测器和文档配置。

每一步都必须先增加失败测试，再做最小实现，并形成可独立回滚的提交。
