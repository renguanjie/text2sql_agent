一、整体运行流程

从服务器启动到用户拿到 SQL，系统按下面的链路运行。非技术视角可以理解为：先把说明书和地图加载好，再根据问题找到相关地图，最后让模型按地图写 SQL。

1. 启动start_server.sh 读取 .env，准备日志、依赖目录和 Streamlit 监听端口。
2. 初始化ApplicationContext 统一创建 LLM、Neo4j、MySQL、Embedding、检索器和 SQL 链。
3. 加载知识优先从 Neo4j 读取图谱；未启用时回退 MySQL 元数据，并建立检索索引。
4. 用户提问用户输入自然语言，例如“查询高收入客户及贷款余额”。
5. 生成 SQL检索相关表字段、获取 Few-Shot、拼装 Prompt、调用 LLM 生成 SQL。
6. 校验与执行SQLFluff 和执行前安全校验后，只允许 SELECT 类查询执行，并保存历史。

二、按顺序拆解模块

下面按系统启动和调用顺序介绍每个模块。每一层只做自己的事，层与层之间通过清晰的数据结构传递信息。

1. 配置层
config.py + .env
读取 MySQL、Neo4j、LLM、Embedding、检索、SQL、日志和启动参数。所有敏感信息应只放在服务器 .env，不要写进源码。
2. 启动层
scripts/start_server.sh
面向服务器的一键启动脚本：创建 python_deps/，把依赖安装到项目目录内，设置 PYTHONPATH，再执行 python -m streamlit run app.py。
3. UI 层
app.py
系统主入口，包含侧边栏配置状态、知识库管理、SQL 生成、执行历史、知识图谱构建入口和系统信息。
4. 生命周期层
core/app_context.py
统一管理组件初始化顺序：LLM → Neo4j → MySQL → Embedding → Retriever → SQLChain → SQLGenerator → 知识库索引。
5. 知识层
core/knowledge/neo4j_client.py
负责 Neo4j 连接、查询、图谱导入导出、子图覆盖、知识库清空、图谱统计，是知识库管理的核心服务。
6. 检索层
core/retrieval/bm25_tfidf.py
把表说明、字段说明、历史成功 SQL 建成可检索文档，结合 BM25 关键词和 FAISS 向量召回。
7. 生成层
core/chain + core/sql/generator.py
SQLGenerator 编排方言检测、知识检索、Schema 获取、Few-Shot、Prompt 生成、SQL 提取、历史保存和执行。
8. 存储层
MySQL + Neo4j
MySQL 保存历史记录、执行状态和基础元数据；Neo4j 保存更丰富的图谱结构和关系权重。

三、知识库如何构造

知识库不是一个单表清单，而是一张可查询、可权重调整、可导入导出的数据库知识图谱。它让模型知道“有哪些表、表里有什么字段、表和表如何 JOIN、哪些业务概念对应哪些表”。

数据来源

DDL 文件：CREATE TABLE JSON 文件：结构化元数据 活体数据库：INFORMATION_SCHEMA 历史 SQL：JOIN 提取增强

DDL 适合离线初始化，活体数据库适合同步真实库结构，JSON 适合迁移或人工整理后的元数据，历史 SQL 用于发现真实业务中经常使用的连接关系。

图谱节点与边

Database Table Column BusinessConcept HAS_TABLE HAS_COLUMN CONNECTS MAPPED_TO / RELATED_TO

核心边是 CONNECTS，它记录表间连接字段、JOIN 类型、预编译 JOIN SQL、权重和来源。

抽取 Extract

GraphBuilderPipeline 根据来源选择抽取器：OfflineExtractor 解析 DDL，OfflineJSONExtractor 解析 JSON，LiveDBExtractor 连接真实数据库读取元数据。输出统一的 SchemaExtractResult。

标准化 IR

抽取结果会被整理成 DatabaseIR、TableIR、ColumnIR、RelationshipIR、BusinessConceptIR。统一 IR 的好处是后续 AI 增强、JOIN 编译、Neo4j 装载不用关心数据最初来自哪里。

AI 语义增强 Enrichment

如果启用 LLM，系统会自动生成业务标签和业务概念，并在缺少显式外键时推断潜在表关系。非技术人员可以理解为：模型帮表结构补充“业务含义”和“可能怎么连”。

JOIN 预编译 Compiler

compile_join_sqls 根据关系生成可复用 JOIN 片段，后续生成 SQL 时模型能看到更确定的连接路径，降低编错关联字段的概率。

装载 Loader

Neo4jGraphBuilder 使用 UNWIND + MERGE 批量写入图谱：数据库连表，表连字段，表与表通过 CONNECTS 连接，概念映射到表。

权重管理

关系带有 weight、occurrence_count、source。历史 SQL 中频繁出现的 JOIN 可以反哺图谱，权重越高，Prompt 中越优先展示。

四、自然语言生成 SQL 的可解释流程

这部分解释“用户问一句话之后系统到底做了什么”。它的核心是：先限定数据库知识范围，再让 LLM 在这个范围内生成 SQL。

步骤模块做了什么为什么需要
1SQLGenerator接收用户问题、会话 ID、目标方言或数据库 ID。提供统一入口，避免 UI 直接操作多个底层组件。
2SQLDialectDetector根据用户问题或指定参数判断 SQL 方言和目标数据库。不同库语法不同，例如 MySQL、PostgreSQL、Oracle 的日期和分页写法不同。
3KnowledgeRetriever用 BM25 + FAISS 检索相关表、字段和历史示例。让 LLM 只关注相关知识，减少上下文噪声。
4Neo4jClient / MySQLClient读取 Schema：表、字段、CONNECTS 关系、JOIN SQL 和权重。Schema 是 SQL 生成的事实依据。
5SQLGenerationChain把用户问题、Schema、知识检索结果、Few-Shot 示例组装成 Prompt。Prompt 是模型的“任务书”，决定输出格式和约束。
6LLM生成 SQL 或返回信息不足。把自然语言意图翻译成结构化 SQL。
7SQLValidator用 SQLFluff 做语法校验，并执行前检查危险语句。降低无效 SQL 和误执行写操作的风险。
8MySQLClient保存生成历史、执行结果、错误和反馈。便于审计、复盘、Few-Shot 学习和后续修复。

五、知识库导入导出与兼容性

新的完整导出格式 导出 JSON 现在使用 version: 2.0，同时包含完整 nodes 和 edges。这能保存所有节点属性和所有关系属性，避免旧格式只导出部分字段、部分关系。
为什么旧逻辑有漏洞 旧导入用字段名作为唯一键，不同表中的 id、name 等字段会被合并；旧导出没有完整记录所属表、数据库和所有关系，导出再导入无法还原原图。
对象唯一定位方式说明
Databasedatabase_id，没有时按 name支持配置文件或 JSON 中存在多个数据库。
Tabledatabase_id + name不同数据库中同名表不会冲突。
Columndatabase_id + table_name + name不同表中的同名字段不会冲突。
CONNECTS / REFERENCES表对 + 关系类型 + 源字段 + 目标字段 + 来源同一对表可以有多条不同字段连接关系。

上传 JSON

用户在侧边栏“知识库管理”上传 JSON 文件。系统先解码 UTF-8，再解析 JSON。

格式校验

如果 JSON 语法错误或结构缺失，界面提示格式异常，并提供“下载模板”按钮。

数据库冲突检测

系统从 JSON 中提取所有数据库引用，查询 Neo4j 中是否已有同名或同 ID 数据库。

覆盖确认

如果存在，弹窗式区域提示用户确认覆盖；确认后只删除这些数据库对应的子图。如果不存在，直接导入。

完整重建

导入 nodes 后再导入 edges，恢复 Database、Table、Column、BusinessConcept 以及它们之间的完整关系。

九、面试逐字稿

下面这段可以直接照着说。语气按“我理解项目、我知道为什么这样设计、我能讲清楚落地价值”的方式组织，适合 5 到 8 分钟介绍。

1. 开场介绍

面试官您好，我介绍一下我这个 Text2SQL Agent 项目。这个项目的目标是让用户用自然语言提问，系统自动生成符合数据库结构的 SQL。举个例子，用户可以输入“查询高收入客户及其贷款余额”，系统会先理解这个问题，再去知识库里找相关的表、字段和表之间的关联关系，最后生成可以执行的 SQL。

它不是简单地把问题直接丢给大模型，因为那样很容易出现表名、字段名、JOIN 条件编错的问题。我的设计思路是：先构建一个数据库知识库，再让大模型基于这个知识库生成 SQL。也就是说，大模型不是凭空猜，而是在有数据库地图的情况下工作。

2. 整体架构介绍

整个系统可以分成几层。第一层是前端交互层，用的是 Streamlit，用户可以在页面上输入问题、查看生成 SQL、执行 SQL、查看历史记录，也可以管理知识库。

第二层是应用上下文层，也就是 ApplicationContext。它负责统一初始化系统里的核心组件，比如 LLM、大模型客户端、Neo4j 图数据库、MySQL、Embedding、检索器和 SQL 生成器。这样做的好处是组件的生命周期比较清晰，不会到处散落全局变量。

第三层是知识库层，主要使用 Neo4j 来保存数据库图谱。图谱里面有数据库节点、表节点、字段节点、业务概念节点，以及表和表之间的 CONNECTS 关系。这里的关系会记录连接字段、JOIN 类型、JOIN SQL、权重和来源。

第四层是检索和生成层。系统会先通过 BM25 和 FAISS 做混合检索，找出和用户问题最相关的表、字段和历史 SQL 示例，然后把这些信息放进 Prompt，再调用大模型生成 SQL。

第五层是存储层。MySQL 主要保存生成历史、执行结果、反馈记录和基础元数据；Neo4j 主要保存更复杂的知识图谱关系。

3. 用户提问后的执行流程

用户输入一个自然语言问题之后，系统会按几个步骤处理。

第一步，SQLGenerator 接收用户问题。它会判断当前要使用的 SQL 方言，比如 MySQL、PostgreSQL 或 Oracle。如果用户指定了目标数据库，就按指定数据库处理；如果没有指定，就根据配置和图谱信息做默认判断。

第二步，系统会进行知识检索。检索器会根据用户问题，在知识库里找相关的表、字段、业务概念和历史成功案例。这里用的是 BM25 加 FAISS 的混合检索。BM25 更擅长关键词匹配，FAISS 更擅长语义相似度匹配，两者结合可以提高召回质量。

第三步，系统会获取 Schema 信息。也就是把相关表有哪些字段、字段类型是什么、表之间怎么关联、JOIN 条件是什么取出来。

第四步，把用户问题、Schema 信息、知识检索结果和 Few-Shot 示例组合成 Prompt，交给大模型生成 SQL。

第五步，对生成的 SQL 做校验。系统会用 SQLFluff 做语法校验，同时执行前只允许 SELECT 查询，避免出现 DELETE、DROP、UPDATE 这类危险操作。

第六步，如果用户选择执行 SQL，系统会执行查询并把执行结果、执行状态和错误信息保存到 MySQL 历史表里。后续这些成功记录也可以作为 Few-Shot 示例，反过来提升下一次生成效果。

4. 知识库是怎么构造的

这个项目比较关键的一点是知识库构造。知识库可以通过三种方式构造。

第一种是 DDL 文件。比如我们上传 CREATE TABLE 语句，系统会解析表名、字段名、字段类型、主键、注释等信息。

第二种是 JSON 文件。这个适合把已经整理好的结构化元数据导入系统，或者做知识库迁移。

第三种是连接活体数据库。系统可以读取 INFORMATION_SCHEMA，直接从真实数据库抽取表结构。

抽取完成后，系统会把结果统一成一套中间表示，也就是 DatabaseIR、TableIR、ColumnIR、RelationshipIR 和 BusinessConceptIR。这样不管数据最开始来自 DDL、JSON 还是数据库，后面的处理流程都是统一的。

接下来会做 AI 语义增强。比如大模型可以给表生成业务标签，也可以根据字段命名推断表之间潜在的关联关系。然后系统会预编译 JOIN SQL，把表之间常用的连接方式保存下来。

最后通过 Neo4jGraphBuilder 把这些信息写入 Neo4j，形成一张数据库知识图谱。图谱结构大概是：Database 连接 Table，Table 连接 Column，Table 和 Table 之间通过 CONNECTS 表示关联，BusinessConcept 和 Table 之间表示业务概念映射。

5. 图谱导入导出为什么要优化

我对知识库导入导出也做了优化。原来的逻辑有一个问题：导出 JSON 时只导出了一部分信息，而且字段节点只按字段名保存。这样如果两个表都有 id 字段，导入时就可能把两个 id 字段合并成一个节点，导致图谱不完整。

所以我把导出格式升级成 version 2.0。新的格式会导出完整的 nodes 和 edges。节点里包含 Database、Table、Column 和 BusinessConcept，边里包含 HAS_TABLE、HAS_COLUMN、CONNECTS 等完整关系。

同时，我给不同对象设计了更准确的唯一定位方式。数据库用 database_id 或 name 定位，表用 database_id 加表名定位，字段用 database_id 加 table_name 加字段名定位。这样不同数据库、不同表里的同名字段就不会互相冲突。

导入时，系统会先校验 JSON 格式。如果格式不对，页面会提示异常，并提供模板下载。如果 JSON 中的数据库图谱已经存在，页面会提示用户是否覆盖；用户确认后，只覆盖这个 JSON 涉及的数据库子图，而不是清空整个图谱。如果数据库不存在，就直接导入。

6. 配置和部署怎么做

配置方面，项目通过 config.py 读取环境变量，实际部署时把 env.example 复制成 .env，然后填写服务器上的 MySQL、Neo4j、LLM 和 Embedding 配置。

MySQL 配置主要用于保存历史记录和执行结果。Neo4j 配置用于启用知识图谱。LLM 配置决定调用哪个模型，比如 OpenAI、Azure、Ollama，或者兼容 OpenAI 协议的模型服务。Embedding 配置用于语义检索。

部署上我增加了一个 start_server.sh 脚本。它会自动创建 python_deps 目录，把 Python 依赖安装到项目内部，不污染系统 Python。它也会读取 .env，然后启动 Streamlit 服务。服务器上只需要解压项目包，配置 .env，然后执行这个脚本就可以启动。

7. 项目亮点总结

我认为这个项目的亮点主要有五个。

第一个亮点是知识增强。SQL 不是让模型凭空生成，而是结合数据库图谱、字段信息、表关系和历史示例来生成。

第二个亮点是图谱化建模。数据库、表、字段和业务概念都存在 Neo4j 里，表之间的关系还有权重，可以随着历史使用不断增强。

第三个亮点是混合检索。BM25 负责关键词匹配，FAISS 负责语义匹配，Few-Shot 负责提供成功案例，所以整体生成会更稳定。

第四个亮点是可解释性。用户可以看到命中的知识、生成的 SQL、校验结果、执行结果和历史记录，不是一个黑盒。

第五个亮点是工程可部署。项目有配置模板、一键启动脚本、独立依赖目录和服务器部署包，更接近真实项目交付。

8. 如果面试官问我项目不足

如果说不足，我觉得主要有几个方向可以继续优化。

第一，权限控制还可以加强。因为 Streamlit 本身没有完整的登录鉴权，生产环境最好放在内网，或者前面加 Nginx、SSO 或 VPN。

第二，依赖版本需要持续维护。因为 LangChain、Streamlit 和 SQL 解析相关依赖更新比较快，后续应该定期做漏洞扫描和兼容性测试。

第三，SQL 的执行安全还可以做得更细。现在主要限制 SELECT 查询，后面可以增加行数限制、超时控制、敏感表黑名单和字段脱敏。

第四，图谱质量可以继续提升。比如引入人工审核流程，让业务人员确认 AI 推断出来的关系是否正确，再写入正式图谱。

最后收尾可以这样说 总结一下，这个项目本质上是一个面向数据库查询场景的知识增强智能体。它用 Neo4j 构建数据库知识图谱，用 BM25 和 FAISS 做知识检索，用 LLM 生成 SQL，用 MySQL 保存历史和反馈。它解决的核心问题是：让大模型生成 SQL 时不再凭空猜测，而是基于真实数据库结构、表关系和历史经验来生成，从而提高准确率、可解释性和可维护性。
